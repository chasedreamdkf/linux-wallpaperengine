linux‑wallpaperengine 移植为 Hidamari‑style GNOME Wayland 后端方案

目标：在 GNOME 50 Wayland 下复用 Almamu/linux‑wallpaperengine 完整壁纸解析渲染内核（支持 Wallpaper Engine Scene / Shader / CEF 网页 / 视频壁纸），借鉴 Hidamari 的架构绕开 Mutter 缺失 zwlr_layer_shell_v1 的限制，不依赖 layer‑shell，不切换 Xorg。

现状问题回顾

1. 原版 linux‑wallpaperengine Wayland 后端依赖 zwlr_layer_shell_v1，GNOME (Mutter) 并未实现该协议，无法把独立窗口放到桌面底层。
2. Hidamari 的解法：外部进程解码 + GNOME Shell GJS 扩展，把画面帧注入 Mutter/Clutter 的内部背景组 _backgroundGroup。
3. 本方案：复用 linux‑wallpaperengine C++ 渲染内核，新增「GNOME Shell 扩展后端」作为输出驱动，实现完整 WE 壁纸能力。

整体架构
整体分为两个独立组件，通过 IPC 完成双向通信。

组件：linux‑wallpaperengine（C++ 后端）
角色：完整解析 WE 壁纸（Scene / CEF 网页 / 视频），离屏渲染到 FBO；输出帧缓冲区；接收鼠标、显示器信息
运行进程：独立用户进程（非 gnome‑shell）

组件：GNOME Shell GJS 扩展
角色：向 _backgroundGroup 插入 Clutter.Actor 作为背景图层；接收后端帧并渲染；上报鼠标位置、显示器配置给后端
运行进程：gnome‑shell 主线程

通信二选一：

- D‑Bus（原型快速验证）：每一帧传递 RGBA pixel buffer，开发简单；4K60fps 存在 CPU 拷贝开销。
- POSIX 共享内存 SHM（正式版）：使用 /dev/shm 共享像素内存，降低拷贝开销，推荐最终实现。

硬性限制：Mutter/GJS 没有公开稳定 API 实现跨进程 OpenGL 纹理共享，只能 GPU→CPU 回读像素再传给扩展，存在性能开销，Hidamari 同样受此限制。

源码修改：为 linux‑wallpaperengine 新增 GnomeShellDriver
该项目原有抽象输出层 VideoDriver，已有 Wayland / X11 / GLFW 驱动，新增 GnomeShellOpenGLDriver，不改动壁纸解析、CEF、Scene 渲染核心逻辑，仅替换输出模块。

1. CMake 修改
新增编译开关，控制是否编译 GNOME Shell 后端驱动。

option(GNOME_SHELL_BACKEND "Enable Hidamari‑style GNOME Shell extension backend for GNOME Wayland" OFF)

if(GNOME_SHELL_BACKEND)
add_subdirectory(drivers/gnomeshell)
endif()

2. 新增驱动文件
路径：src/drivers/gnomeshell/GnomeShellOpenGLDriver.cpp/.h

驱动核心逻辑：

1. 初始化：建立 D‑Bus / SHM 通道，等待 GNOME Shell 扩展就绪；
2. 复用现有渲染管线，将壁纸渲染到内部离屏 FBO m_sceneFBO；
3. 每帧渲染完成，从 FBO 回读 RGBA 像素缓冲区；
4. 将像素数据写入共享内存 / 通过 D‑Bus 发送给 GJS 扩展；
5. 接收扩展回传信息：显示器分辨率、多显示器布局、鼠标坐标；
6. 将鼠标坐标输入传给壁纸引擎，实现视差、鼠标驱动特效；
7. 处理信号：进程退出时释放共享内存、关闭 IPC 连接。
8. 命令行参数扩展
新增启动参数，触发该后端：
linux-wallpaperengine --gnome-shell /path/to/steam/workshop/wallpaper_id

识别 --gnome‑shell 参数后，实例化 GnomeShellOpenGLDriver，跳过 Wayland/X11 窗口创建逻辑。
注意：该模式下完全不创建任何 Wayland/X11 可见窗口，全部为离屏渲染。

扩展安装路径：~/.local/share/gnome‑shell/extensions/linux‑wallpaperengine‑gnome@local

extension.js（核心伪代码）
import * as Main from 'resource:///org/gnome/shell/ui/main.js';
import Clutter from 'gi://Clutter';
import Gdk from 'gi://Gdk';
import Gio from 'gi://Gio';
import GLib from 'gi://GLib';

export default class Extension {
enable () {
// 创建背景渲染 Actor，插入 GNOME 内部背景组 _backgroundGroup
this.wallpaperActor = new Clutter.Actor ();
// Hidamari 多显示器修复 hack
this.wallpaperActor.set_style ('background-color:rgba (0,0,0,0.01);');
Main.layoutManager._backgroundGroup.add_child (this.wallpaperActor);

this.setupDBus();
this.setupMouseMonitor();
}

setupDBus () {
// 建立 D‑Bus 服务，等待 C++ 后端连接
// 1. 接收来自后端的帧数据（width, height, rgba_bytes）
// 2. 将 bytes 转为 Gdk.Texture，设置给 wallpaperActor
// 3. 上报显示器列表、屏幕尺寸给后端
}

setupMouseMonitor () {
// 获取鼠标坐标，通过 D‑Bus 发送给 C++ 后端，用于壁纸视差交互
}

onNewFrame(width, height, pixelBytes) {
const bytes = GLib.Bytes.new(pixelBytes);
const texture = Gdk.Texture.new_from_bytes(bytes, width, height);
this.wallpaperActor.set_content(texture);
}

disable () {
this.wallpaperActor?.destroy ();
// 通知 C++ 后端退出，清理 IPC 资源
}

}

扩展能力清单

1. 将渲染 Actor 插入 _backgroundGroup，置于桌面图标下方；
2. 多显示器兼容（依赖 rgba (0,0,0,0.01) 经典 hack）；
3. 上报显示器配置、鼠标坐标给 C++ 后端；
4. 接收画面帧更新纹理；
5. 扩展禁用时销毁 Actor，通知后端停止渲染；
6. 可区分桌面 / 锁屏状态，锁屏时暂停壁纸渲染，避免壁纸覆盖锁屏界面。

注意：Main.layoutManager._backgroundGroup 属于未公开内部 API，没有稳定性承诺。GNOME 大版本升级可能发生重构、改名，所有同类扩展 (Hidamari/Blur‑My‑Shell) 都面临该风险。

实现路线选择：原型版 vs 正式性能版

路线 A：D‑Bus + RGBA 像素拷贝（快速原型，优先做）

- 优点：开发门槛低，不需要处理 POSIX 共享内存复杂逻辑；C++ 与 GJS 不需要处理 OpenGL 跨进程同步。
- 缺点：4K 60fps 每一帧传递大量像素，CPU 占用较高。适合验证整体链路通不通。

路线 B：POSIX 共享内存 SHM（正式版本）

1. C++ 后端分配 /dev/shm 共享内存段；
2. FBO 回读的 RGBA 像素直接写入共享内存；
3. GJS 扩展映射同一块共享内存读取像素；
4. 使用信号量同步帧生产 / 消费，防止撕裂。

- 优点：大幅减少内存拷贝，降低 CPU 占用，适合高分辨率高刷新率。
- 缺点：增加 IPC 同步逻辑。

已知硬性限制与坑点

1. gnome‑shell 主线程压力
GJS 扩展运行在 gnome‑shell 主线程，高频更新纹理会造成 shell 卡顿、概览动画掉帧。
对策：后端做帧节流，对齐显示器 VSync，不要无限制全速推送帧。
2. GNOME 版本强绑定
GJS / Clutter / Mutter API 在大版本之间会变动；扩展仅针对 GNOME50，升级 GNOME 后大概率失效，需要修改扩展代码。
3. 无法实现壁纸内鼠标点击交互
_backgroundGroup 的 Actor 不会接收鼠标点击事件；WE 网页壁纸的点击交互无法实现（Hidamari 同样存在该限制）；仅鼠标位置视差特效可用。
4. 内部 API 风险
_backgroundGroup 不是官方公开 API，未来版本随时可能修改。
5. 锁屏界面干扰
Actor 默认会渲染到锁屏背景，需要额外逻辑区分桌面 / 锁屏，锁屏时隐藏 Actor。
6. CEF 网页壁纸额外负担
linux‑wallpaperengine 的 CEF 编译本身复杂度高，网页壁纸会增大内存占用。

推荐开发实施顺序

1. 最小原型验证
   - 修改 linux‑wallpaperengine，实现离屏渲染，输出帧到 SHM/D‑Bus；
   - 编写极简 GJS 扩展，读取帧并渲染到 _backgroundGroup；
   - 先用简单视频壁纸测试链路，暂时跳过 CEF 网页壁纸。
2. 完善双向 IPC
   - 扩展上报显示器信息、鼠标坐标；后端接收并驱动壁纸交互；
   - 调试多显示器布局。
3. 接入完整 WE 渲染管线
   - 测试 Scene / Shader / 粒子壁纸；调试 CEF 网页壁纸输出。
4. 性能优化
   - 帧节流、VSync 对齐；切换到 SHM 零拷贝路径；优化内存拷贝。
5. 打包部署脚本
   - 编译引擎二进制；提供一键安装脚本，自动部署 GNOME Shell 扩展到用户扩展目录。

方案对比

原版 linux‑wallpaperengine
实现原理：独立 Wayland 客户端 + layer‑shell
GNOME Wayland：不工作
WE Scene 原生壁纸：完整支持
网页壁纸：CEF 支持

Hidamari
实现原理：外部 VLC 解码 + GJS 扩展注入背景组
GNOME Wayland：支持 GNOME50
WE Scene 原生壁纸：不支持
网页壁纸：仅视频 / 简单网页

本改造方案
实现原理：linux‑wallpaperengine C++ 内核 + GJS 扩展注入背景组
GNOME Wayland：支持 GNOME50
WE Scene 原生壁纸：完整支持
网页壁纸：CEF 支持

备选折中方案（不修改 C++ 源码）
如果不想 fork 修改 linux‑wallpaperengine 源码，理论可以使用外部桥接：

1. 让原版引擎运行在纯离屏模式，输出帧到共享内存；
2. 独立 GJS 扩展读取共享内存渲染。

前提：原版项目需要暴露离屏渲染输出接口。若无该接口，则必须修改 C++ 源码。
